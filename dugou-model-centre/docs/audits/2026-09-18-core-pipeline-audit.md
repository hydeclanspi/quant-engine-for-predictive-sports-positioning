# DuGou 核心算法审计

审计日期：2026-09-18。代码基线：`49e4622`。

## 结论与边界

系统并不是空壳：确实实现了历史校准、原子收益状态、分数 Kelly、组合搜索、均值—方差式分配、回测和结算反馈。但目前还不能把它视为一套已通过完整样本外验证、概率语义一致的量化决策模型。

最重要的问题不是“模型不够高级”，而是：**训练目标、概率口径、历史身份、决策分布和验证路径没有完全统一。** 在这些基础未修好前，继续增加相关性修正、自学习系数或模拟次数，不能证明准确性提高。

本次完成核心计算路径静态审读、跨模块调用核对、现有测试执行以及合成反例验证；没有修改生产算法、真实数据或配置，没有推送。新增的文件仅为本报告与只读复现脚本。

这不是实盘收益审计：没有读取当前云端完整真实账本，没有重建所有历史预测时刻的信息集合，没有证明任何策略具有正的样本外收益。反例说明代码能够产生某类错误，不代表你的每一笔历史投资都受到了同样影响。

### 证据强度

- **复现**：直接执行当前源码中的函数，以合成数据得到结果。
- **静态确定**：可从字段、公式及调用路径确定；实际历史影响尚未量化。
- **研究风险**：模型假设或验证设计存在局限，不能仅凭代码断言现实中一定有偏或一定亏损。
- **P1**：优先处理，会影响概率、金额、反馈学习或验证可信度。**P2**：次优先，主要影响约束、解释、诊断或边界行为。不设“必须推倒重来”的预设。

## 1. 算法全貌

主计算文件 `src/lib/analytics.js` 共 6436 行，审读覆盖全文件；同时核对 `atomicParlay.js`、`ComboPage.jsx` 的生成/分配/模拟/采纳路径，以及 New、Settle、localData、settlementQuickInput、Params 和 FragilityHeatmapCard 中与算法有关的生产调用。UI 大段 JSX、主题样式、云同步服务的完整协议和权限安全不是本次覆盖目标。

| 子系统 | 实际做什么 | 主要入口 |
| --- | --- | --- |
| 概率与情境校准 | 原始 Conf → AJR 线性回归与二元命中 PAV 混合 → Mode/TYS/FID/FSE 因子 → Conf×Odds、球队残差、市场锚定 | `analytics.js:1906`, `2456`；`NewInvestmentPage.jsx:712`；`ComboPage.jsx:1974` |
| 原子收益与新建仓位 | 同场 Entry 切分状态、等分投入，跨场乘积合并收益；最大化期望对数增长后除以 Kelly divisor，再截到风险限额 | `atomicParlay.js:219`, `339`, `416`；`NewInvestmentPage.jsx:773–847` |

| 回测与自适应 | 历史回归、Brier/LogLoss、Kelly 候选除数比较；历史分桶启发式更新超参数；结算后更新部分权重 | `analytics.js:550–1074`, `2268`, `2858`, `3803–5323` |
| 依赖风险诊断 | 相近赔率历史对的共同失败统计、收缩、两两 FGM 参数与 Shapley 式分摊、热力图 | `analytics.js:5324–6436`；`FragilityHeatmapCard.jsx:77–181` |

它更准确的定位是“以用户判断为输入的、历史校准驱动的投资决策系统”，不是 DeepSeek 在预测比赛。AI 快捷录入主要负责结构化输入和结算辅助，不负责核心赔率优势估计。

### 几个需要区分的概念

- Conf 是用户给出的量；AJR 是赛后评级；`is_correct` 是命中标签；利润取决于实际兑付。四者不是同一个目标。
- 命中任一 Entry、整串命中、整张票盈利，三者也不同。
- Portfolio 最终分配不是新建页那套完整原子 Kelly 的直接复用：它先优化权重，再分配风险预算。
- “globalJoint”是在经过筛选的有限候选池上搜索，不是整个原始组合空间与金额空间的全局最优证明。
- 热力图的脆弱性分数不是概率。其两两 FGM/Shapley 诊断也不是 Portfolio 所有收益计算共同使用的完整多维联合分布。

## 2. 优先修复项

### A01 · P1：平均评分被当作整串概率，且同一持久化字段存在两种含义

**证据：静态确定 + 复现 `KELLY_SEMANTICS`。**

新建页 `NewInvestmentPage.jsx:817–821, 1036–1038, 1104` 把各场校准概率的算术平均写入 `expected_rating`。Portfolio 在 `ComboPage.jsx:3735, 5186` 将整串命中概率写入同名字段。`analytics.js:563–601` 的历史 Kelly 输入却不区分来源，直接把该字段当作整笔投注成功概率。

两个独立单选事件的概率均为 0.6、赔率均为 2：平均是 0.6，整串概率是 0.36。初始资本 1000、四分之一 Kelly、风险上限 12% 时，当前回测函数分别给出 116.67 和 36.67。这里展示的是**回测口径错误**；新建页即时仓位另走原子分布，不能把这三倍差异直接称为线上实际多投了三倍。

**修改思路：** 拆分 `raw_conf`、`calibrated_hit_probability`、`ticket_hit_probability`、`ticket_profit_probability`、`expected_return`、`judgment_score`。每笔保存预测版本及分布快照。旧数据按来源迁移；无法确定含义的旧字段标记 unknown，不猜测补全。多状态票不能继续套单一二项 Kelly 回放。

**验收：** 两腿 0.6 的独立单选串关得到 0.36；同一个业务对象从 New/Portfolio 建立后，核心字段语义一致；历史回放使用保存时的预测。

### A02 · P1：验证的模型不是线上真正执行的完整模型

**证据：静态确定。**

生产线性校准 `analytics.js:1906–1944` 的标签是 `AJR / 0.8`。验证路径 `2750–2763, 2268–2318, 2858–2898` 将二元命中 0/1 填进 `match_rating` 后拟合同一回归函数。它在验证的是命中校准，不是原先的 AJR 评级校准。

生产路径还叠加 PAV、情境因子、赔率桶修正和不同的市场融合；验证主要评估线性、球队与一个简化市场融合。这些指标不能直接代表完整线上策略。PAV 的 `brierImprovement` 在拟合使用的同一批数据上计算（`4270–4286`），是训练集描述，不是泛化证据。

此外，历史按投资 `created_at` 切分（`2765–2781`），结算写入没有统一的 `settled_at / outcome_available_at`（`SettlePage.jsx:776–810`）。同一比赛出现在多张票里会被展开成多条记录。仅按记录创建顺序，无法保证训练中的赛果在预测测试记录时已经可知，也无法保证同一比赛不横跨两边。这是**可发生的信息泄漏风险**，本轮没有声称已在真实账本量化其发生比例。

Kelly 除数选择 `analytics.js:904–1005` 在各测试窗口上比较候选并选最高分，训练段并未用来选择该窗口的除数。如果再把这些窗口的最好成绩当作最终样本外成绩，就把调参集误当成了独立测试集；作为调参过程本身则可以保留。

**修改思路：** 提取单一 `fit(history, config)` / `predict(snapshot, input)` 生产管线，由线上和离线共同调用。概率模型以真实二元命中为目标；AJR 保留为独立研究信号。按 `event_id` 分组，训练样本必须在预测时已经结算；内层调参、外层按时间评估，并冻结最终留出集。保留原始 Conf 与赔率隐含概率两个基线。

**验收：** 每个历史测试点能列出完整训练数据范围和版本；修改未来结果不改变过去预测；同场多票不能跨训练/测试；Brier、LogLoss、可靠性图和实际账本回放都针对同一个生产版本。独立数据评估与嵌套选择的原则见 [概率校准文档](https://scikit-learn.org/stable/modules/calibration.html) 和 [嵌套验证文档](https://scikit-learn.org/stable/auto_examples/model_selection/plot_nested_cross_validation_iris.html)。

### A03 · P1：PAV 未合并相同 Conf，结果随样本排列变化

**证据：复现 `PAV_TIES`。**

`analytics.js:4204–4268` 先按 conf 排序，但相同 conf 仍分成不同块；查询时命中第一个同横坐标节点。

60 条历史全部 conf=0.5，30 中、30 失，仅把输入顺序反过来：校准输出从 **0.02 变为 0.50**。两者的可靠度都为 0.5，已经足以进入生产混合校准。这不是不同超参数导致的变化。

**修改思路：** 先按唯一 conf 聚合样本权重与标签和，再进行加权 PAV，输出唯一横坐标节点。样本量和可靠度另用样本外证据控制，不能用修复 tie 的方式掩盖小样本风险。

**验收：** 同一数据任意排列输出一致；预测函数单值、单调、有界；与成熟保序回归实现做固定样例对照。官方实现也明确处理 ties，见 [IsotonicRegression](https://scikit-learn.org/stable/modules/generated/sklearn.isotonic.IsotonicRegression.html)。

### A04 · P1：组合质量检查被窗口门槛跳过；缺失时间仍通过时间检验

**证据：复现 `EMPTY_QUALITY_CHECK`、`MISSING_TIMESTAMPS`。**

- `analytics.js:95–97, 4863–4923` 的测试窗口为 7 条；`4775–4778` 却要求至少 8 条，否则返回 quality=1。外层仍将这些窗口累计成有效质量评估。
- 50 条全中与 50 条全失都得到 `enabled=true, windowCount=3, quality=1`，命中率字段为 null。这里的 1 是“没有执行检查时的默认值”，不能解释成质量优秀。
- `781–805` 的缺失日期转成 epoch 0，并被视为有效日期。30 条完全没有时间戳的记录仍得到两个 walk-forward 窗口。Kelly 分桶在 `1723–1728` 恰好没有保留日期。

**修改思路：** 统一测试窗口与评估门槛；无评估返回显式 unavailable，不能伪装成中性成功。缺失时间拒绝时间验证或进入明确的非时序诊断；分桶传递原始事件/可用时间。

**验收：** 缺失时间不会生成已验证时间窗口；正反结果能改变有数据时的质量指标；无数据时 UI 显示未评估，不显示可信度已通过。

### A05 · P1：自动学习的开关、特征和优化目标均未与生产一致

**证据：复现 `DISABLED_AUTO_WRITES`、`FEATURE_SCHEMA`、`INACTIVE_CONF_WEIGHT`；目标函数为静态确定。**

1. `localData.js:92–102` 有 enabled、mode、updateEveryN；但 `analytics.js:5249–5320` 没有执行这些门禁。Settle 三条确认路径 `890, 955, 996` 无条件调用自动应用。合成 60 条记录，在 enabled=false、mode=disabled 时仍触发配置保存。
2. `analytics.js:3845–3865` 读取旧字段 `tys_base_home / fid_base_home` 和顶层 mode；现代新建存储的是 `tys_home / tys_away / fid / matches[].mode`。S/H、FID=0.75、单场“保险产品”的合成记录，被提取成 TYS=0.5、FID=0.5、Mode=0.5。
3. `weightConf` 会参与自适应更新，却没有参与 New/Portfolio 的当前概率公式。仅将其从 0.25 改到 0.65，合成输入概率完全不变。
4. `analytics.js:3905–3943` 优化的实质是 `Σ(历史利润 × 特征加权和) / Σ历史投入 - 0.1 × |历史平均亏损金额|`。历史选单与投入不会随候选权重重新计算；亏损惩罚对权重是常数，梯度为零，且将金额与无量纲 ROI 相减。它不是对实际决策策略收益的梯度优化。“confidence”来自梯度大小乘样本量，也不是统计置信概率。

**修改思路：** 先尊重 disabled/suggest/auto 和更新频率，使用唯一特征提取函数。明确删除无效控制项还是接入真实模型。概率权重用样本外 proper loss 训练；决策参数若要学习，必须在冻结历史信息的情况下重放真实选单与仓位。试验版本先仅给建议，经过验证才晋升。

**验收：** disabled 零写入；同一结算数据重复触发幂等；批量和逐笔不会因调用次数不同偷偷改变学习幅度；特征对照表逐项匹配生产字段；所有标为有效的参数都有敏感性测试。

### A06 · P1：复盘用“球队对”关联结果，可能把另一场或另一盘口当作标签

**证据：复现 `RETRO_IDENTITY`。**

`analytics.js:4522–4550, 4580–4629` 仅按 `home vs away` 关联历史，没有比赛日期、盘口或事件 ID。`getInvestments` 按最新到最旧返回（`localData.js:1269–1286`），Map 持续覆盖，最终还可能留下旧结果，注释中的“最新”并不成立。

合成同球队两次交手：最近一次命中、旧的一次未中；针对最近比赛的两条推荐被复盘为 0% 命中。即使修正排序，同场不同盘口仍会混淆。多个方案反复使用同一比赛，还会把同一赛果重复当成学习证据。

**修改思路：** 建立稳定 `event_id + market_type + line + selection`，另存 ticket_id；Plan snapshot 明确引用 event/selection 及创建时预测。无法匹配的旧数据留为 unknown。训练可靠度按独立事件或事件簇统计，不能按生成过多少方案计数。

**验收：** 改另一日期的同队比赛结果不影响当前复盘；同场不同盘口分别判定；追加重复推荐不增加独立样本量。

### A07 · P1：相关性估计受腿顺序影响；概率修正后收益分布没有一起改变

**证据：复现 `ENTRY_ORDER`、`CORRELATION_DISTRIBUTION_SPLIT`。**

`analytics.js:4432–4467` 对 pairKey 排序，却不按同一顺序排列 a/b 边际计数。20 个组合的内容不变，仅交换其中 10 个的腿顺序，返回 rho 从 0 变到 -0.5。这个构造中的常数边际本身不适合定义相关系数；结论不是“真实 rho 应为 0”，而是**数据的表示顺序不能制造新相关信号**。

`ComboPage.jsx:3392–3426` 对 p 和 profitWinProbability 做修正，但 ev、variance 仍取修正前的独立原子分布。合成例子中 p 从 0.36 变成 0.38，EV 仍为 0.44。于是概率门槛、仓位输入、收益展示并不描述同一个随机对象。

**修改思路：** 先修正有序边际累计；常数边际返回不可估计。不要把 phi 直接视为通用概率增量。若引入相关性，必须生成满足边际和可行边界的统一联合状态，从它同时推导 p、盈利概率、EV、variance 和模拟。样本不足时明确保留独立近似，而不是给未验证修正高置信标签。

**验收：** 腿排列不变性；概率和为 1；所有边际满足边界；解析均值/方差与模拟一致；rho=0 可以退化到独立版本。

### A08 · P1：Monte Carlo 丢失多 Entry 的收益形状，并把零投入变为模拟投入

**证据：复现 `MC_DISTRIBUTION`、`ZERO_STAKE`。**

`ComboPage.jsx:399–504` 为每条腿抽二元命中，再按条件平均赔率兑付，没有抽 `atomicProfile.states`。等价赔率能保住某些场景的均值，但不能保住盈利概率、方差和尾部。

同场两项：win @2、lose @8，各分一半资金；unionProbability=0.8。现有原子模型给出的净收益状态是：64% 回本、16% 盈利 3 倍、20% 全亏。所以盈利概率是 **16%**。当前 50000 次 MC 却给 **79.786%**。两者期望利润分别约 28 和 27.66（投入 100），平均值接近恰好说明仅验证均值不够。

`534–539` 遇到 amount=0 会转用理论权重百分数或默认 10；0 元、25% 理论权重的备用方案变成了 25 元模拟投入。这种“假想等权篮子”可以是单独分析模式，不能与实际金额模拟混用。

共享抽样已经比完全独立抽每张票更合理；但 key 多为记录 ID 或带 Entry 的字符串，同一物理赛事在不同记录/盘口中仍未必共享同一个赛果。

**修改思路：** 使用赛事级联合场景，每轮每场只抽一个结果，再计算所有市场、票据的真实 payout。实际模拟严格使用 funded tickets 与实际金额；假想组合单列并标注。用确定性枚举的小案例作为模拟 oracle。

**验收：** 上述盈利概率约 16%，而不是 80%；零投入不改变 P&L；同场互斥选择不能同时命中；VaR/盈利概率与枚举结果在蒙特卡洛误差内一致。

### A09 · P1：原子模型并不支持任意盘口的重叠语义

**证据：复现 `EXHAUSTIVE_OUTCOMES`，其余为静态确定。**

`atomicParlay.js:158–177` 仅对能解释为胜/平/负集合的条目共享原子；其他条目各自生成独立的 `entry_i` 原子，等价于认为它们互斥。例如“2-0”和“win”本可同时命中，当前通用 fallback 没表达这种重叠。

`200–208` 的并集估计统一使用 `1 - Π(1 - p_i)`，这是独立事件并集公式，不适用于互斥且完备的胜/平/负。三项赔率都为 3、三结果全覆盖时，原子 profile 仍生成 **29.63% 全部不中**。对于按正常完赛胜平负定义的三项，这种状态不可能发生；赛事取消等特殊结算应单独建 void 状态，而不是这种 miss 分支。

**修改思路：** 明确支持的市场及结算规则。精确比分/胜平负/让球等通过同一个赛事状态评价器计算命中集合与回报；不能可靠解释的混合 Entry 显示“不支持精确概率建模”，不静默假设互斥。多选分配权重应存档，不能只留一个等价赔率。

**验收：** 完备覆盖无普通 miss；子集事件不会比母事件概率更高；相同比分能同时兑付重叠 Entry；已知互斥事件不会同时命中。

### A10 · P1/P2：上限变成了预算目标，且默认覆盖约束可无解

**证据：复现 `NO_CASH_OPTION`、`NO_FEASIBLE_COVERAGE`。**

- `ComboPage.jsx:1806–1866, 3049–3082, 3650–3685` 采用归一权重并分完整风险预算；没有现金资产或“所有候选都不值得投”的自动退出。合成的候选 EV 全负（-84% 至 -93.6%）仍将 120 的风险额度全部分配。若用户明确选择强制花完预算，这可以是产品模式；但默认称为 Kelly/最优投资建议就不准确。
- 默认单组合覆盖率 55%，组合最多五腿。选择十场互异赛事时上限为 5/10=50%，生成 null。不是样本太差，而是约束数学上不相容（`1385–1391, 3288–3293, 3341–3342, 3533–3536`）。
- 当前蓄水池是本金加已结算盈亏，没有扣除未结算在途暴露（`analytics.js:1086–1132`）；风险上限是每次生成的上限，不等于账户总风险上限。重复采纳是否会超出用户期望，取决于产品对该上限的定义，应明确并加入全局约束。

**修改思路：** 把现金保留为可选解；风险上限用 ≤ 而非必须花完。区分“预算花完模式”与“风险最优模式”；把在途最坏损失、可用资金和本轮预算分别建模。组合级与组合包级覆盖率分开命名，并在搜索前做可行性检查。

**验收：** 全负 EV 且无强制下注要求时零投入；已有在途风险纳入限额；十场/五腿/55% 应清晰提示无解或提供用户确认的放宽选项，不能默默改变约束。

### A11 · P2：软惩罚和覆盖加分被下游原始 utility 重排覆盖

**证据：复现 `SCORE_DISCARDED` + 调用链静态确定。**

`ComboPage.jsx:2802–2822` 生成 softUtility；`1241–1275` 覆盖加分生成 boostedUtility，但起点仍是原 utility；`1156–1170` 分层时又按原 utility 排序。`3553–3583` 正是这条生产调用链。

反例：候选 A 的修正后得分 10、原始 utility 1，B 的修正后得分 0、原始 utility 2；同腿数只取一个时选了 B。不能笼统说所有覆盖逻辑完全无效——下游另有 MMR 与补覆盖——但这两项分数不是被一致地消费。

**修改思路：** 显式定义 baseScore → penaltyAdjustedScore → coverageAdjustedScore → diversityScore，所有排序器传同一个明确的 score accessor；诊断时展示每阶段淘汰原因。

**验收：** 固定其他因素，仅增大某项惩罚，相关方案的受控阶段排名不会反向提高；覆盖权重变化能在专用案例中改变候选选择。

### A12 · P2：依赖风险的显著性和百分比解释不成立

**证据：复现 `WEIGHT_SCALE_PVALUE`、`NO_DATA_RISK`，其余静态确定。**

- `analytics.js:5740–5745` 注释称使用 ESS，实际把权重和作为二项试验次数。完全相同十个历史样本，同一加权比例、同一 ESS≈10，仅把所有核权重乘 2：p 值从 0.02791 变成 0.001877。任意核权重的整体量纲不应制造新增证据。
- 这些还是赔率邻近、重复组合、经过最佳配对筛选的数据；即使把权重和换成 ESS，也不会自动得到严格的独立同分布二项检验。多对同时检验还有多重比较问题。
- 没历史、赔率均为 2 时，当前输出 score=25、low、confidence=0.05，而不是不可估计。
- `FragilityHeatmapCard.jsx:140–181` 默认按当前矩阵中位数和 IQR 做相对 sigmoid 映射；中位数映成 44.5。它是相对视觉分数，不是该 pair 失败概率。即使有“映射增强”开关，也不宜继续用概率式百分比解读。
- `adjustForBaseRate` 计算全局失败率但不让它决定修正，只按溢价正负乘 0.8/1.2；所谓 propensity matching 实际为赔率桶匹配。Shapley 分解的是一套边乘积代理函数，不应解释为真实联合尾部事件的因果分摊。

**修改思路：** 分清相对风险指数、共同失败率估计、区间和显著性。无数据返回 unknown。以事件/日期簇重采样评估不确定性；按实际采样机制设计检验，多重比较再控制错误发现。修复前保留这些指标作探索诊断，避免将其当作概率或自动调仓依据。

**验收：** 权重统一缩放不改变估计及证据强度；零历史不宣称低风险；增加其他候选不改变一对的原始风险估计；相对颜色与绝对数值明确分离。

## 3. 需要研究验证，而不能直接判为 bug 的部分

### 3.1 AJR 是评级，不天然是命中概率

即使 AJR 除以 0.8 后落在 [0,1]，也不因此成为 Bernoulli 标签。一个未命中但判断质量尚可的 AJR=0.4 会产生 0.5 训练目标。自动“命中→0.8”使二者部分重合，但未命中端仍不相同。

可保留 AJR 作为独立的判断质量目标；若希望它提高命中概率预测，需要证明它的历史衍生特征在预测时可知，并在独立未来数据上带来增益。它不是必须删除的字段。

### 3.2 情境因子存在混杂和重复修正风险

`learnContextFactors` 比较各桶命中率与全局命中率，未控制原始 conf、赔率、市场类型。保险产品本来就可能集中于低赔率、高命中事件；高命中不自动等于赔率之外的额外优势。相同结果又被线性/PAV、赔率桶、球队、情境、超参数层反复使用，可能重复计入同一信号。

这不是证明这些因素无用。建议以市场/原始 Conf 为基线，用少量正则化参数建模残差，通过按时间和事件分组的消融实验逐层验证。没有稳定增益的层先保持中性，而不是从代码名字推断有效。

### 3.3 超参数学习更多是启发式映射，不是完整策略搜索验证

`backtestComboHyperparams` 用命中率、Brier、分桶 ROI 映射出几十个系数，然后按样本数增加信任；`backtestDynamicParams` 用 AJR 散点和阈值构造动态参数。这样的经验规则可以是初始设计，但不等于每个系数都经过独立回测，也不保证每次结算后表现改善。

应记录参数学习自由度、独立事件数、实际选参过程；使用外层时间测试检验整个学习算法，而不只检验某个子回归。不要把同一赛事重复出现的几十张票当作几十次独立预测证据。

### 3.4 赔率锚定和“去水”不代表已识别市场真实概率

`calcConfSurplus` 使用 `1/odds × (1-vig)`，vig 又由已选历史样本估计。只拿被选中的某一项赔率，不能唯一识别同一时刻全盘口超额概率及其分配。可以称之为“市场参考概率的假设调整”，不宜把与其之差直接称为套利或已证实市场定价错误。

建议保存同一市场全部可比报价和时间；若没有，就报告 overround 假设的敏感性区间，并以未去水的隐含概率作透明基线。

### 3.5 协方差和路径风险仍为近似

`ComboPage.jsx:2964–3047` 的相关系数由重叠率/Jaccard 加常数构造，并不是从同一组收益场景估出的协方差。代码没有检查正半定性或给出最优性残差；本审计没有声称已在某个真实组合上找到负特征值。

推荐从统一收益场景矩阵生成 covariance（天然半正定），必要时收缩、检查数值条件，再验证约束残差和优化收敛。独立近似可以作为基线，不要求为了“高级”强行上复杂 copula。

Kelly 历史 bootstrap 固定初始资本算 stake、重采样记录，不是严格复现资金冻结/释放、复利、停手机制的事件账本。因此它能作分布探索，不能直接等同真实账户路径风险。增加到十万次只是降低这套假设内的模拟噪声，不增加历史样本证据。

## 4. 次要但应纳入修复清单的口径问题

- `analytics.js:1534–1600` 球队 ROI 包括 pending 记录；`splitInvestmentToMatches` 把缺失收入视为 0，未结算的投入便暂时表现为负利润。已实现收益应与在途敞口分开。
- `analytics.js:210–229` 按腿数均分本金、按腿赔率分收入，这是人为归因，不是真实单腿收益。它适合明确标注的归因报表，不应无说明进入单腿仓位学习。
- `analytics.js:3416–3419` Sortino 分母使用负收益子集的标准差，而不是相对目标收益的 downside deviation。相同幅度的多次亏损会给出零分母；Sharpe 的 √笔数缩放也不是统一时间年化。须先定指标定义，再统一显示。
- `getPerMatchEjrSnapshot` 仍将 raw conf 与原始 0–0.8 AJR 直接相减；它不是校准后的概率误差，命名应明确。
- New 前端接受“正数赔率”，原子模型却只接受 >1；≤1 的 Entry 可能被过滤并回落到默认赔率。应统一十进制赔率校验，不能静默改变有效用户输入。
- 单场预览 `ComboPage.jsx:1779` 的 `max(20, min(riskCap,...))` 可以越过小于 20 的 riskCap；New 在负 poolBalance 时还需验证负推荐金额边界。与 Portfolio 最终总额分配应分别测试，不混为一个路径。
- `FragilityHeatmapCard` 历史读取缓存依赖为空、归档过滤与其他 analytics 不同；会造成同一时点不同视图取样不一致。需要统一 dataset selector 和 revision。
- New/Portfolio 有 lite→full 的异步校准阶段。若允许在 full 准备前保存，需要记录实际使用的模型阶段，否则同样输入可能因操作时机不同生成不同预测。

## 5. 建议修复顺序和研究验收

### 第一阶段：先恢复确定性和数据契约

1. 增加 event/market/selection 身份、结果可用时间、模型版本及预测快照；保留原字段，做可回滚迁移。
2. 修复 PAV ties、pair 边际方向、回测 7/8 门槛、缺失时间、旧字段读取和自动学习门禁。
3. 将无数据、未验证、失败和中性分别表达；不再用默认 1 代表已评估。
4. 将复现反例转换为正式 regression/property tests。当前复现脚本断言的是“旧缺陷存在”，不能原封不动当作修复后的验收测试。

### 第二阶段：统一数学对象

1. New、Portfolio、模拟、回测共用“赛事状态 → 票据收益”的函数。
2. 从同一分布推导命中率、盈利概率、EV、variance、Kelly 与 Monte Carlo。
3. 加入现金选项、在途风险与金额取整后的约束复检；统一评分流水线。
4. 不支持的市场明确拒绝精确建模，不拿默认状态替代真实语义。

### 第三阶段：证明增量价值

按日期顺序保留外层测试，内部做小规模调参；至少对照：赔率隐含概率、原始 Conf、单一校准、完整候选管道。

- 概率：Brier、LogLoss、可靠性图及分桶样本数/区间。Brier 同时包含区分度与校准信息，不能只凭 Brier 下降就宣称校准更好。
- 决策：以当时可得赔率和真实 payout 规则逐事件回放，包含未下注、未结算资金、整数单位、风险上限与费用（若有）。同时报告下注覆盖率，防止只展示筛后命中率。
- 不确定性：按物理赛事或日期簇做 bootstrap，而非随机拆同场腿；报告性能差异的区间。数据不足时结果应是“尚无法区分”，不是强行选赢家。
- 稳健性：参数小扰动、赔率变化、顺序交换、同场多票复制、零资金、全负期望、约束无解、小样本、单类标签、无日期。
- 晋升机制：保存稳定版本与试验版本，在影子模式下对照；达到预先约定的稳定性及外层评估要求后才启用自动更新。不要根据同一份测试结果反复改规则然后继续称它为测试集。

## 6. 应保留的基础，不应为找问题而否定

- 已有命中与盈利概率区分、原子收益状态和对数效用 Kelly，这是正确的抽象方向；问题在支持范围和下游一致性。
- 模式/球队/相关性估计有向先验收缩，说明已考虑小样本；需要改进可靠度估计，不是取消收缩。
- 模拟有确定性随机种子，适合回归比较；应继续保留并增加分布级 oracle。
- 使用 Brier、LogLoss、时间窗口和市场基线的方向合理；重点是确保验证完整生产对象且无泄漏。
- 组合覆盖、集中度约束、手动风险偏好可以是正当产品需求，不必全部替换成单一学术最优目标。但“偏好”与“模型预测事实”要分离。
- Demo 数据与 Live 数据存在隔离；本次没有用 Demo 表现、合成 UI 指标或模拟次数证明实盘有效性。
- 现有 162 项测试全部通过，基础功能有回归保障；但通过它们不能证明统计性质和策略有效性。
